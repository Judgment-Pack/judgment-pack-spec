# Adversarial review: RFC 0031, "Annotations and annotated value sets" (Draft), at commit 4cae6a3

This review was produced by a model from the same vendor as the model that assisted the drafting. It is therefore **not** the different-vendor review that RFC 0009 requires, and it does not count toward Evidence bar item 1.

## Verdict

**Do not accept at this commit. Accept after the changes listed below.**

The evaluation form (§4) holds up. I found no way for two conforming evaluators to reach a different disposition, error class or precedence for a conforming pack, beyond the numeric seam Core already has.
- An evaluator written for this review from the Core text and the RFC alone agrees with all 73 staged rows.
- The evaluation form of every valid staged case is a valid pack, both under the draft schema and under the `0.3.0` schema with the selector changed.

Three things block acceptance:
1. **Display safety rests on a false premise.** The RFC refuses bidirectional embeddings and overrides so that "a label can [not] display in an order other than its logical one". The marks and isolates it admits do exactly that, and unbalanced isolates defeat the plain-text isolation that D1 relies on (H1). Filtered views can also omit rules without any visible sign, because the D1/D2 safeguards that would prevent it are only SHOULDs (H2).
2. **Unresolved question 4 is framed as a clarification of released `0.3.0` text** while the repository's released checker keeps the other reading. On that framing, a released pack changes meaning (H3).
3. **The RFC's own evidence bar is unmet.** Items 1, 3 and 6 are not met; items 2, 5 and 7 are partly met. Graduating also involves steps the RFC does not yet describe (M4–M7).

## Unresolved questions

1. **Ceilings: answer now, accepting the numbers as reasoned.** Measuring them needs packs that use the shapes, which cannot exist until the version opens, so waiting for measurement is circular. The numbers err low, and raising them under a later selector cannot invalidate a pack. One condition: the disposition should state that the byte limit is the only aggregate bound on annotations. There are 66,560 characters per object at `base`, and the number of annotated objects is unbounded.
2. **More positions: safe to defer.** A later selector that admits more positions only turns refused shapes into admitted ones. Packs written to the accepted version contain none of them, so their evaluation form is unchanged. The later record must extend evaluation-form step 3 to the new positions.
3. **Where the two advisories live: safe to defer, on one condition.** Do not mint the two codes in the released Core text in the meantime. Advisories never change conformance, so no pack can break. Minting codes in Core text now would fix names that RFC 0027's contract might want to change. Keep §3.3.1 to the reading of a reference as its set (the overlap-check rule), and add the advisories when RFC 0027 is dispositioned.
4. **The `extensions` reading: answer now. Deferral is not safe.**
   - Recommended answer: the narrow reading, counting only `extensions` objects the schema defines.
   - Why it is not optional: the evaluation form needs it. Under the broad reading, a required name found only in the value of an unreferenced set's entry is present in `P` and absent from `EF(P)`. `EF(P)` would then not be semantically conforming, which breaks §4.1's guarantee.
   - The broad reading also counts objects whose keys break §9's own key grammar (`"Bad"` in `valid-extensions-member-in-data`).
   - State it as a change under the new selector, per H3.

## Verified sound

- **Harness and carry-over.** All 31 tests pass. Every released document case holds under the draft selector. With the selector replaced, the 20 released and 15 staged `0.3.0` evaluation rows give the same results under the draft schema (independent evaluator).
- **Hand-written expectations.** All 73 staged rows match an evaluator written from Core §8 and the RFC. It covers type-preserving equality with exact decimals, `in`, `not`/`all`/`any`, exceptions, handoff to a target, and §8.4 order. That includes `1` against `1.0` (match), `"1.0"` against `"1.00"`, NFC against NFD, booleans against strings (no match), object member order (match), and the unresolved reference beside malformed evidence (`pack-not-conformant`).
- **Evaluation form.** For every valid staged case, the evaluation form is valid under the draft schema and under `0.3.0`. That supports the "migrating down" claim.
- **Condition positions.** The schema has exactly the four the RFC names: applicability, a rule's `when`, an exception's `when`, and nesting under `all`/`any`/`not`.
- **Schema behaviour.** The `not` plus `type` construction gives a single type error for a non-string list item. The `if`/`then`/`else` reference rule produces the codes the RFC states.
- **Required extensions under the evaluation form.** The preservation argument holds: sets have no `extensions`, and entries admit annotations only.

the fixes. The fixes are in the same pull request as this record.

| # | Severity | Disposition | What changes |
|---|---|---|---|
| H1 | HIGH | **Accept** | The rule for annotation keys is unchanged: the key grammar is ASCII. Annotation strings refuse every bidirectional format character: U+061C, U+200E, U+200F and U+2066–U+2069 join the refused class, beside U+202A–U+202E. The reasoning that admitted marks and isolates, and its false claim about marks, are removed. D1's isolation rule for display stays. The cases that admitted marks or isolates are replaced, and refusal cases are added. |
| H2, M8 | HIGH, MEDIUM | **Accept** | Annotation strings also refuse (a) the invisible and default-ignorable characters U+00AD, U+034F, U+115F–U+1160, U+17B4–U+17B5, U+180B–U+180F, U+200B–U+200D, U+2060–U+206F, U+3164, U+FE00–U+FE0F, U+FEFF, U+FFA0, U+FFF0–U+FFF8, U+1BCA0–U+1BCA3, U+1D173–U+1D17A and U+E0000–U+E0FFF, which covers the tag characters; and (b) a string that begins or ends with a Unicode White_Space character, listed exactly in the RFC. A string made only of white space is thereby refused. The RFC states the cost: emoji sequences that need a zero-width joiner or a variation selector, and scripts that use the joiners for shaping, cannot appear in an annotation, which is a short machine-comparable label; free text belongs in `description`. The ranges outside the Basic Multilingual Plane must work in the `pattern` under ECMA-262 in Unicode mode, RE2 and Python `re`; a range that cannot be made portable is kept as a semantic rule with its own case, and the record says so. D2 makes two things MUST: a filtered view states the matched and total counts; and wherever distinct values are listed or a filter is stated, every character outside printable ASCII in a key or value is shown unambiguously. D2 adds that a review made from a filtered view covers only what the view showed and is not a review of the pack. |
