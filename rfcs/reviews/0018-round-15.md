## Findings

### 1. HIGH: the grammar's "path" leaves out the leading `/`, which the matching rule needs

`spec/dialect.md:739` and `:763-767`; `rfcs/0018-dialect.md:1484` and `:1508-1512` (byte-equal).

- **What happens.** The form reads "then either nothing or `/` and a path". Taken literally, the
  path is what follows the `/`. The matching text treats the path as including that `/`: "An absent
  prefix path or `/` admits every path", with the examples `/docs` and `/docs/`. On the literal
  reading, the root prefix `https://a.example/` has the empty path, which is neither absent nor
  `/`. It then admits only `https://a.example/` and `https://a.example//...`, and "a path equal to
  `/`" would mean the URL `https://a.example//`.
- **The readers.** Both include the `/` in the path (`(/[^?#\\]*)?`, `prefix_path in ("", "/")`).
  They admit every path under `https://a.example/`. Two implementations can give opposite answers
  for the root prefix, so a reader and the literal text disagree.
- **Also.** "Compare hosts with ASCII `A` to `Z` treated as `a` to `z`" never says the hosts must be
  equal.
- **Fix (words only, no reader change).** "then either nothing or a path, which begins with `/`".
  For hosts: "the hosts are equal, ASCII `A` to `Z` compared as `a` to `z`".
- **Confirmed by** reading the text and both readers' code. The readers' answers were confirmed by
  running the probes "empty endpoint path vs scope /", "endpoint / vs absent scope path" and "scope
  root // vs /x" (`.review-scratch/probe.log`).

### 2. MEDIUM: the Gateway writes a third spelling of port 443, `host:`, which the form refuses

This is a false refusal of an honest receipt. `spec/dialect.md:736-739` and `:768-770`;
`rfcs/0018-dialect.md:608-611` and `:1513-1515`.

- **What happens.** At Gateway dd31264 (the v0.17.0 code; the tag adds only notes):
  - `attachment.WebURL` admits an empty port: `u.Port()` is `""` and `u.String()` round-trips.
  - `sameOrigin` follows a redirect to it.
  - adapter-web writes it as `acquisition.endpoint`.
- **The probe.** Through the adapter's own TLS fixture, on a scratch copy:
  - request `https://example.com:/docs/x` gives the endpoint `https://example.com:/docs/x`;
  - `Location: https://example.com:/hop` gives the endpoint `https://example.com:/hop`.
- **Why it matters.** That is the same page as `https://example.com/hop` (RFC 3986 §6.2.3). The form
  ("either nothing or `:443`") refuses it, so both readers give `acquisition-invalid` for an honest
  receipt of a page inside the scope (probe "endpoint empty port"). The claim "They admit host case
  and either spelling of port 443 as the Gateway writes them today; no new Gateway normal form is
  required" is therefore incomplete.
- **The cited form.** `SPEC.md` §1.2a is the Gateway's form for a remote MCP server's URL (shape
  `mcp` with `transport`). That form itself refuses `:` with no port, and adapter-web's endpoint is
  not held to it.
- **Other spellings checked, which are fine:**
  - an uppercase host and `:443` are written by the Gateway and admitted by the form;
  - fragments, Unicode hosts and trailing dots are refused by the Gateway first;
  - raw characters in a Location are written escaped (`%22`, `%5C`, `%C3%A9`);
  - dot segments in a Location are resolved;
  - a requested `/docs/../x`, or a Location `/a/%2e%2e/b`, is written as it is and refused by the
    form, as intended.
- **Fix, one of:**
  - admit `:` followed by nothing as a third spelling of port 443, in the form and in matching. This
    keeps "no new normal form".
  - state the refusal, and file a Gateway follow-up in which adapter-web refuses or normalizes an
    empty port.

  In either case, describe §1.2a as the remote-server URL form this one restricts, not as the web
  adapter's form.
- **Confirmed by** running (`.review-scratch/gateway-endpoints.json`, plus both readers).

### 3. MEDIUM: `https://*` on a `record` web profile makes every page a `record` source

`spec/dialect.md:727-734` and `:751-758`; `rfcs/0018-dialect.md:597-602` and `:617-625`.

- **What happens.**
  - The member is admitted on a `record` profile for the `web` kind, and the wildcard is allowed in
    any scope.
  - A `web` source's `url` may be a `$param` naming a case parameter.
  - With `https://*`, any page the operator names is therefore read as class `record`, with no
    generated influence.
  - §8.2 admits `record` to every target by default.
- **What changed.** Before this round, a `web` record profile pinned one reviewed URL, and `record`
  meant "a signed read of a system" that the installation had classified.
- **Why it is a finding.**
  - The RFC justifies the wildcard by research's need ("A company's origin is not known..."), whose
    class is `generated`.
  - It says `web` has "the same need", but not what `record` then means.
  - §13's new entry establishes nothing about how wide the scope is.

  So the classification adds no meaning for this binding, and the text does not say so.
- **Fix, one of:**
  - admit `https://*` only on a `generated` page profile (research), and require prefix entries on a
    `record` profile;
  - state in §§5.1, 8.2 and 13 that a wildcard `record` profile classifies every public page as
    `record`, and that a dialect narrows such targets with `admits`.
- **No reader is affected today.** Both refuse `web` as `kind-unread`, and the Runner refuses it by
  name.
- **Confirmed by** reading.
