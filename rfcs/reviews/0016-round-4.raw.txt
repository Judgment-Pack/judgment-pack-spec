**Findings**

**F1 — MAJOR — The carrier qualification does not reconcile the portable contract.**

R:168–169:

> “Whether a document that holds a string with an unpaired surrogate is admitted is the carrier's matter, and §2.1 does not settle it.”

R:479–481 repeats the premise:

> “§2.1 requires an implementation to reject malformed input and does not say whether a JSON text that holds an unpaired surrogate escape is malformed.”

Core §2.1 does not independently prescribe scalar-only strings, but neither does it leave JSON syntax unspecified: line 65 incorporates RFC 8259. That RFC’s grammar admits unpaired surrogate escapes; §8.2 discusses their interoperability problems. Its §9 also permits restrictions on string character contents. Consequently, **syntactically malformed JSON, a permitted documented carrier restriction, and a nonportable interpretation are different claims**. The amendment does not distinguish them.

RFC 8785’s rejection of lone surrogates concerns canonicalization. Core §12:827–828 incorporates it for disposition comparison, not for canonicalizing every facts document. A facts string that never reaches the disposition does not, merely by existing, make that disposition unserializable.

The unresolved problem is visible in Core itself:

- §8.2:609–610: “Two conforming implementations therefore agree on which inputs are admitted at all”.
- §8.3:674–679 identifies exactly one arithmetic exception and says no other implementation-relative escape exists in §§7–8.
- §10:777–779 separately excludes inputs above documented implementation limits.

The amendment allows `malformed-input` versus an `unresolved` disposition without identifying which of these rules authorizes the distinction. Meanwhile, the unchanged R:191–192 says:

> “The byte-identity requirement of §8.3 extends to `value`.”

Thus the amendment exposes an interpretation/portability issue, but presents carrier discretion more conclusively than the combined sources warrant. It does not establish that both behaviors are conforming.

**Smallest edit:** Describe the observed difference as an unresolved Core admission issue. Distinguish syntax from permitted documented restrictions; identify the required Core clarification in *What this needs from Core*; qualify the portability discussion accordingly. Question 9 may remain open at Draft, but any proposed additional portability exception must be explicit and reconciled with §§8.2–8.3 before acceptance.

**F2 — MINOR — Declaration includes implementation advice as specification text.**

R:130–132:

> “An implementation that admits the name by setting it aside before it validates the rest has to check for the second itself, and for the name listed twice, since what it set aside is what the validator would have read.”

The checks are correct. Core §9:758–760 requires a corresponding extension value; schema:413–419 requires unique required-extension entries. But the sentence describes the runtime’s projection/validator architecture rather than an externally observable requirement.

**Smallest edit:** State the invariants directly: a required name needs its corresponding declaration, and `metadata.requiredExtensions` must remain unique. Move the projection explanation to *Implementation*, or label it an informative implementation note.

R:406–407:

> “The cases this document lists under Conformance and Examples were written out as 60 rows, each with a pack of its own and the answer this text gives, and run through both.”

**Smallest edit:** Say “60 selected concrete rows derived from the pre-amendment RFC”; identify the omitted example cases and the unexercised future-schema consumer. Alternatively, complete the coverage before retaining the comprehensive claim.

**F6 — MINOR — Question 9 overstates which evaluations the carrier question affects.**

**C. Normative text and open questions**

The declaration clarifications are substantively sound. Core §4:265–267 distinguishes recognized Core members from extension payload data. Schema:106–112 permits arbitrary extension values, and schema:517 permits arbitrary fact-comparison operand values where other operator constraints do not narrow them. A nested member merely named `extensions` therefore neither declares outcome values nor satisfies `metadata.requiredExtensions`.

The required-name-without-declaration paragraph also correctly distinguishes two faults:

- A value in another legitimate extension slot satisfies Core’s existence requirement but violates this RFC’s placement rule.
- No corresponding value anywhere violates Core §9.
- Duplicate entries violate schema `uniqueItems`, independently.

Only the implementation-specific last sentence needs relocation under F2.

The resolution paragraph correctly distinguishes preflight from value resolution and correctly prevents lone surrogates from entering a canonical disposition. Its defect is the stronger interpretation of conforming carrier freedom described in F1.

For the rewritten Conformance text:

| Implementation profile | Unique expected result? | Assessment |
|---|---|---|
| Admits the surrogate-bearing facts document and supports the extension | Yes: unresolved/unknown for the stated selected value | Valid conditional value-resolution case |
| Refuses that facts document at preflight | Yes: malformed-input | Describes the observed branch; does not establish the refusal is conforming |
| Schema admits the name, extension unsupported, declaration valid/empty/unknown type | Yes: unsupported-required-extension | Properly scoped future-consumer cases |
| Published schema rejects the name | Yes: pack-not-conformant | Correct current-consumer cases |
| Duplicate pack member, either support setting | Yes: pack-not-conformant | Correct carrier fault and precedence |

The surrogate bullet is effectively two conditional cases. It can state one answer per named admission profile, but it cannot establish implementation-independent conformance by classifying an implementation according to whatever it happens to accept. The Core decision in F1 must settle that standing.

| Unresolved question | May remain open at Draft? | What settles it |
|---|---|---|
| **1. Extension or Core** | Yes | Select the form and specify its schema/version integration and evaluator obligations. Both prototypes choosing extension supplies no comparative experiment against Core form. |
| **3. Reuse `unknown`** | Yes | Decide whether portable consumers need a distinct reason; specify any reason/trigger changes or retain diagnostics outside the disposition. The trace demonstrates one diagnostic approach, not that the distinction is unnecessary. |
| **8. Bounds** | Yes | Choose portable bounds/accounting or explicitly retain documented local limits, including the work-accounting differences now reported. Core §10 permits differing local limits. |
| **9. Surrogate carrier treatment** | Yes, as an unresolved issue | Reconcile RFC 8259 syntax and permitted restrictions with Core admission, error and portability requirements; then state the applicable conformance cases. Current wording overstates what is settled. |
| **10. Combination with RFC 0008** | Yes | Specify joint admission/version support and combined work accounting, with joint cases. “Whichever is accepted second should say” identifies sequencing, but should name these concrete decisions. |

Question 10’s “what a pack that uses both means” is broader than the actual semantic gap. RFC 0008:175–199 restores the previous condition root after each `where`; RFC 0016 resolves values after outcome selection and selects from the facts document. Ordinary pointer composition is therefore already substantially constrained.

The important unresolved interaction is accounting: RFC 0008:281–294 requires exact admission accounting, and 435–439 defines one running budget along the §8 path. Arbitrary additional outcome-resolution charges cannot simply be assumed compatible with that contract.

After rereading the whole RFC, I found no further material contradiction or false Core/schema description beyond F1, F4 and F6. The statements about the two reserved-name schema sites, four current disposition members, decimal grammar, optional-extension prohibition, reason vocabulary and handoff rules are accurate.

**D. What an acceptance reader could still overestimate**

The nonconformance and nonindependence disclaimers are clear and useful. They do not cure the complete-coverage claim or the attribution of historical fixture expectations to the amended document.

The strongest supported empirical statement is:

> The supplied outputs agree on 59 of 60 synthetic inputs; 56 pairs match the frozen fixture expectations.

That does not establish:

- complete example coverage;
- behavior of a schema-admitting but extension-unsupported consumer;
- portability at resource limits;
- correct combined operation with RFC 0008;
- coverage of the new nested-data, required-without-any-value, or duplicate-required-list clarifications.

Those latter implementation claims come from decision records or textual analysis, not these 60 executions.

“Clean-room” and “different vendor” also remain methodology claims, not independent direction. The specific vendor and shared-model attribution need the qualification in F5.

Finally, A:111–116 explicitly says:

> “It is not in this repository's CI yet.”

The record distinguishes driver/expectation checks in CI from the actual two-implementation comparison. The amendment need not describe every tooling detail, but its results should not be read as continuously reproduced acceptance evidence.
