## Findings

Both findings concern this exact sentence in Evidence item 3, lines 128–133:

> CPEX's modes (`sequential`, `transform`, `audit`, `concurrent`, `fire_and_forget`) run as phases in that order, a phase's plugins by priority, so which result a `tool_post_invoke` hook observes is set by its mode and priority: an `audit` or `fire_and_forget` hook sees the result after every plugin that transforms it, a `sequential` hook of low priority sees it before most of them; ContextForge still accepts its earlier modes (`enforce`, `enforce_ignore_error`, `permissive`, `disabled`) beside these.

### R5-1 — MAJOR: `fire_and_forget` does not receive the chained result

**Source/problem:** CPEX’s documentation and the gateway plugins note suggest the stated behavior, but **CPEX 0.1.3’s code contradicts it**:

- Transformations accumulate in `current_payload`.
- The normal completion path passes the original `payload` to `_fire_and_forget_tasks`, which snapshots that argument.
- The early-halt helper likewise passes the original payload. Background hooks can therefore run even when a blocking plugin prevents subsequent phases.

Consequently, a result-redaction plugin can transform the chained result while a background reporter receives its original contents. Mode ordering alone does not establish the observation claimed here. This directly affects clause 2’s observation and retention contract. [Transformation handling](https://github.com/contextforge-org/cpex/blob/277dfd1752d0f5ed24ae43d9ac26214d2380bc5f/cpex/framework/manager.py#L773), [normal background dispatch](https://github.com/contextforge-org/cpex/blob/277dfd1752d0f5ed24ae43d9ac26214d2380bc5f/cpex/framework/manager.py#L524), [halt handling](https://github.com/contextforge-org/cpex/blob/277dfd1752d0f5ed24ae43d9ac26214d2380bc5f/cpex/framework/manager.py#L996).

**Smallest edit:** Replace the assertion about `audit` and `fire_and_forget` with:

> An `audit` hook, when reached, sees the chained result after the `sequential` and `transform` phases. In CPEX 0.1.3, `fire_and_forget` instead receives a snapshot of the original hook payload and can also be scheduled on an early halt.

The gateway note repeats the same mistake; agreement with that note is insufficient here.

### R5-2 — MINOR: Priority terminology obscures the actual ordering

**Source/problem:** CPEX specifies ascending numeric priority **within serial phases**. ContextForge explicitly calls a lower number *higher priority*. “Low priority” therefore reverses, or at least ambiguously describes, the intended ordering. “Before most” also depends on the configured plugin population. Concurrent and background execution should not be presented as serial execution by priority. [CPEX execution modes](https://contextforge-org.github.io/cpex/docs/0.1.x/execution-modes/#phase-order), [ContextForge configuration](https://github.com/IBM/mcp-context-forge/blob/main/plugins/config.yaml).

**Smallest edits:**

- Replace “a phase’s plugins by priority” with “plugins within each serial phase running in ascending numeric priority”.
- Replace “a `sequential` hook of low priority sees it before most of them” with “a `sequential` hook sees changes from earlier sequential hooks, before later sequential hooks and the `transform` phase”.
