## Findings and verdict (verbatim)

**Verdict: mergeable after fixes F1–F9 below.** The five expected error classes are correct, and both new fixtures have the intended conformance properties. The defects concern publication, the shared checker, test coverage, and several claims in the documentation.

1. **F1 — MAJOR: staged JSON is published despite the stated boundary.**  
   Staged README:21 (`conformance/evaluation/staged/README.md:21`) says: “Not published with the specification” and “reachable in the repository only.”

   `web/build.py:2066`, however, recursively copies all JSON under `conformance`. A dry run with filesystem writes mocked confirmed publication of `cases.json` and all three staged packs under `/artifacts/conformance/evaluation/staged/`. The staged README itself has no site route. `tests/test_site.py:184` actually requires these copies.

   `tools/build_release.py:20` also archives the entire `conformance` directory. The existing release is safe because the builder requires its tagged commit, but a future release retaining staged rows would bundle them.

   **Smallest fix:** exclude `conformance/evaluation/staged/` from site and release artifact selection, and adjust the site-copy test accordingly. Alternatively, retract the repository-only publication claim and describe the actual distribution explicitly; exclusion better preserves the stated boundary.

2. **F2 — MAJOR: the shared checker rejects schema-supported implementation-defined classes.**  
   tests/test_repository.py:700 (`tests/test_repository.py:700`) requires `expected_class` to belong to `{None, "resource-exhaustion"}` when no static preflight error applies.

   Core §8.4 permits a documented implementation-defined class when no Core class applies. `manifest.schema.json:188` expressly supports those names. I replaced a released row’s disposition with `expectedErrorClass: "com.example.timeout"`: the case schema accepted it; the new helper rejected it solely because of this whitelist. That does not establish that the hypothetical timeout is justified, but it demonstrates an unsupported blanket prohibition.

   The original proposal excludes implementation-defined cases from **this batch**; that does not justify narrowing the shared carrier checker.

   **Smallest fix:** when `called_for is None`, reject the three statically excluded Core preflight classes, rather than whitelisting only two results. Leave class-name validation to the schema and preserve the existing Core-precedence check when a Core class is known to apply.

3. **F3 — MAJOR: staging does not exempt an implementation from the existing contract.**  
   Staged README:16 (`conformance/evaluation/staged/README.md:16`) says: “An implementation that disagrees with a staged row has not failed anything.”

   Core §3.4 explicitly scopes a claim to every applicable requirement for every admitted input, not just corpus rows. An evaluator reporting `unsupported-required-extension` for case 5 violates the already-released §8.2/§8.4 contract, even though it has failed no released corpus row. Disagreement needs adjudication; it is not automatically harmless.

   **Smallest fix:** say that disagreement does not itself constitute a released-corpus failure, but may reveal a violation of the normative contract. Scope the adjacent “no claim is affected” language to unchanged corpus obligations.

4. **F4 — MINOR: the migration-cost argument overstates what a new version requires.**  
   RFC 0013:28 (`rfcs/0013-evaluator-error-and-precedence-cases.md:28`) says a new version means “re-declaring every pack, fixture and example and moving every implementation.”

   Core §11 and VERSIONING.md require exact-version matching and separate conformance claims. They do not require existing packs or implementations to migrate. VERSIONING.md explicitly preserves checkability for packs retaining older versions.

   **Smallest fix:** limit the statement to artifacts targeting the new version and implementations choosing to support or claim it. Retaining the decision to stage these rows requires no policy change.

5. **F5 — MINOR: the appended sections incorrectly deny refusal/adversarial coverage.**  
   RFC 0013:241 (`rfcs/0013-evaluator-error-and-precedence-cases.md:241`) says the rows test which refusal occurs, “not whether one happens”; line 244 says an input inducing a disposition where an error is due “is not attempted here.”

   Every error row requires an error instead of a disposition. More specifically, case 2 supplies `request.type: "dataset-deletion"`, making the pack’s applicability false. It therefore catches an evaluator that returns `not-applicable` before checking evidence—the exact trap described by Core §8.2. Removing only the undeclared key produced `not-applicable` in the Python evaluator.

   **Smallest fix:** acknowledge refusal coverage and case 2’s preflight-before-resolution check; mention false applicability in that row’s `focus`. Its expected class needs no change.

6. **F6 — MINOR: the later review cannot retroactively repair the original merge’s process compliance.**  
   RFC 0013:13 (`rfcs/0013-evaluator-error-and-precedence-cases.md:13`) labels this “A lapse this acceptance repairs.”

   GOVERNANCE’s Scope bullet covers creation of a Draft RFC. Its Record and Pull-requests-only bullets attach the review and dispositions to the relevant pull request. Calling the original omission a lapse is correct. Reviewing both proposal and disposition now addresses the missing substantive scrutiny and can satisfy the accepting PR’s obligation; it cannot make PR 64 have met its own merge requirement.

   **Smallest fix:** replace “repairs” with language distinguishing disclosure of the historical violation from completion of the first review now.

7. **F7 — MINOR: the fixture test does not preserve the stated reason for failure.**  
   tests/test_repository.py:849 (`tests/test_repository.py:849`) checks only `len(diagnostics) == 1`, despite citing “one stated reason.”

   In memory, I added a second outcome and changed the rule outcome to an undeclared identifier. The fixture then failed solely for an unresolved reference. **All five staged tests still passed**, while the fixture description, row focus, and adoption decision remained false.

   **Smallest fix:** assert that the sole failure is the outcomes minimum at `/outcomes`, and that this fixture contains one outcome.

8. **F8 — MINOR: the original proposal’s prior-art example is factually wrong.**  
   RFC 0013:210 (`rfcs/0013-evaluator-error-and-precedence-cases.md:210`) describes a positive/adversarial pair and gives `carrier-duplicate-root-member` beside `carrier-duplicate-nested-member` as its example.

   Both entries in `conformance/manifest.json` expect `invalid`. Neither is the positive case.

   **Smallest fix:** describe them as complementary negative cases, or replace the example with an actual positive/negative pair.

9. **F9 — MINOR: the RFC index still equates acceptance with landing.**  
   rfcs/README.md:8 (`rfcs/README.md:8`) says an accepted RFC’s resulting text “lives where the proposal declared it would land.” Its newly changed RFC 0013 entry instead says accepted and staged.

   RFC 0000 defines acceptance as design approval at the named maturity; it does not require simultaneous landing. RFC 0006’s same-merge adoption is a precedent, not a universal requirement.

   **Smallest fix:** distinguish acceptance from incorporation in the introduction and identify RFC 0013 as approved but awaiting incorporation. Keeping `Accepted` is permissible.

Nothing there moves extension support ahead of evidence. Checking that a required extension has a corresponding value is part of pack conformance; checking whether the evaluator supports it is the later capability step.

The fixture checks support the proposal:

- `error-single-outcome.json` produces exactly one structural diagnostic, `JPS-STRUCTURE-COLLECTION-ARITY` at `/outcomes`, and zero semantic diagnostics. A single outcome does not independently violate another reference or cross-field rule here.
- `error-required-extension.json` produces zero structural or semantic diagnostics. `com.example.unsupported-probe` appears both in `metadata.requiredExtensions` and as a root `extensions` key, satisfying §9.
- The copied triage fixture is byte-identical. Both copies have SHA-256 `5bdf53e5c283b5a7c7a04373cfa66a488b021c1e098254424c0de7a963ea8aca`.

Staging itself **honors the freeze**: the requested diff over the released manifest, manifest schema, and `packs/` is empty. Those paths also match the release tag. The staged wrapper has no `suiteVersion`, is not a released manifest, and creates no additional corpus obligation. Editing the explanatory README on mutable `main` is permissible: Core §1.1 explicitly excludes that README from the normative corpus. F1 concerns publication claims and ambiguity, not an actual alteration of the frozen rows.

The static helper’s precedence is sound for these inputs. It returns `pack-not-conformant` before reading evidence declarations, so an unreadable `evidenceRequirements` cannot make the helper choose a lower class. There is an upstream limitation: `_check_evaluation_cases` unconditionally calls `semantic_diagnostics` after structural checking, and an in-memory `evidenceRequirements: null` caused a `TypeError`. That pattern predates this commit; it is not a newly introduced precedence defect.

The evidence-key change preserves rejection for the twenty existing disposition rows. Adding `not-a-declared-requirement: "present"` to a released row while retaining its disposition now fails because the helper requires `malformed-input`; the old check also rejected it. Thus protection for those rows is retained. “Stricter than before” should be scoped accordingly: the overall accepted input set has deliberately expanded to permit correctly labelled error rows.

The five new tests validate the staged wrapper and case schema, shared case checks, fixture coverage, copied bytes, and diagnostic count. The coverage test checks set membership—**at least once**, despite “once” in its name—which fits intentional fixture reuse. F7 identifies the substantive missing assertion. “Eleven deliberate breaks … were each caught” remains an **unverified attestation**; the supplied record does not establish those historical runs.

The implementation-experience paragraph is supported by the supplied source snapshots:

- The Go preflight lives in `internal/evaluation/engine.go`. It defers reporting unsupported extensions until after facts and evidence validation. `TestPreflightOrderIsTheErrorPrecedence` tests that ordering, including undeclared evidence keys.
- Python’s `evaluate()` follows the same sequence. Its precedence test uses `["not-an-object"]`, so the adoption record’s distinction is accurate; separate Python tests also cover undeclared keys.
- `harness/class_agreement.py` compares dispositions. A nonzero exit becomes an error result that cannot count as agreement; it does not compare error classes.
- I independently ran all five through the Python evaluator API: each raised the expected class in preflight and returned no disposition. I inspected, but did not execute, the Go evaluator. The historical claim that both were run by hand remains only partly corroborated by this review.

The phase decision is defensible. §8.4 requires reporting a class, not a separately reported phase. The phase distinction still governs classification, but omitting `expectedErrorPhase` loses no mandatory output assertion for these cases. Only sketches 1–3 explicitly include that field; all five errors nevertheless occur in preflight. Thus “three sketches show it” and “known for all five” are compatible, although the original wording could distinguish those facts more clearly.

Appending RFC 0000’s sections during reviewed acceptance is permissible; it says “should contain” and does not impose a drafting-time deadline. Their substantive inaccuracies are covered above. The implementation-independence shortfall is disclosed and does not prohibit draft-maturity acceptance.

I found no additional stale twenty-row count or unqualified “no error rows anywhere” claim in the requested README, FAQ, TESTING, and `docs/` checks. Those corpus counts remain correct.
