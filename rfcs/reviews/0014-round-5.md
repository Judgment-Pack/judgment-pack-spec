## Findings and verdict (verbatim)

**Verdict: `mergeable after fixes`.** Two MAJOR and four MINOR findings; no BLOCKER.

Reviewed HEAD `b2ee692` plus the five-file diff. Its SHA-256 matches `232649e46abde0d229778814f95a3f71306d6b6e46822cd98bf273022d025f38`. This was a source review; I did not execute suites or demonstrations.

Line numbers below refer to the amended working tree.

1. **R5-F1 — MAJOR: the amendment strikes an independence statement that remains true.**

   **At issue — RFC 0014, L164:** the struck text “no second, independent implementation of the version 3 verifier exists”; L170 then says “two of those three statements were overtaken”.

   **Source:** [`verify-ts/README.md`, L25–39](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/625a24a/verify-ts/README.md#L25) discloses the author’s prior reference-code involvement. RFC 0014 itself rules at L178–180 that this implementation does **not** meet the independence bar. A second implementation now exists; a second independent implementation has not been established.

   The same problem appears at L410–415: “none has been built for version 3’s join” follows “A clean-room second implementation”. Its replacement—“one now has, and it is not clean-room”—changes the antecedent.

   **Smallest edit:** Preserve the independent/clean-room absence statements and add the non-clean-room implementation as a separate development. Change “two … statements were overtaken” accordingly. In the adoption summary and CHANGELOG, describe four developments or updates, rather than four factual statements disproved.

2. **R5-F2 — MAJOR: adoption did not precede filing in every owning repository.**

   **At issue — RFC 0014, L16–17:** “the gateway, the runtime or the demo, each of which adopted its part by its own process before this record existed”.

   **Source:** RFC 0014’s [original PR #74](https://github.com/Judgment-Pack/judgment-pack-spec/pull/74) opened on September 14 at **07:13:50 UTC** and merged at **07:41:38 UTC**. Demo [PR #70](https://github.com/Judgment-Pack/judgment-pack-demo/pull/70) merged at **14:52:34 UTC**; [PR #71](https://github.com/Judgment-Pack/judgment-pack-demo/pull/71) was not even opened until **14:54:08 UTC**, then merged at **14:57:16 UTC**. Built branches and adopted changes are different standings, as Evidence correctly distinguishes.

   **Smallest edit:** Replace “before this record existed” with “before this record’s acceptance”. This preserves the retrospective rationale without rewriting the chronology.

3. **R5-F3 — MINOR: Implementation retains an obsolete implementation count.**

   **At issue — RFC 0014, L409–410:** “Two implementations exist and are not independent: the gateway’s Go verifier and executor, and the runtime’s Go record writer, both by this project.”

   **Source:** The amendment adds a third implementation body, the gateway’s TypeScript verifier, supported by its actual [`verify.ts`](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/625a24a/verify-ts/src/verify.ts). The opening enumeration still presents the original two as exhaustive.

   **Smallest edit:** Add `verify-ts` to the enumeration and adjust the count, or describe the original gateway and runtime components without an exhaustive count. Keep the independence qualification.

4. **R5-F4 — MINOR: the CI claim assigns every vector to the wrong execution path.**

   **At issue — RFC 0014, L174–175:** “the gateway’s CI holds it to every corpus vector through the corpus’s process contract.”

   **Source:** [`go/conform.go`, L212–303](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/625a24a/go/conform.go#L212) runs canonicalization vectors and both store-vector directories through that contract. The corpus also contains Ed25519 vectors, exercised separately by [`verify-ts/test/corpus.test.ts`, L36–46](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/625a24a/verify-ts/test/corpus.test.ts#L36). CI runs both paths.

   **Smallest edit:** Say “every canonicalization and store vector through the corpus’s process contract”—the wording RFC 0015 already uses. The broader claim that CI exercises every vector is supported; the claimed route is not.

5. **R5-F5 — MINOR: the adoption record understates the conditions the process amendment actually introduces.**

   **At issue — RFC 0014, L28–29:** “The condition attached is the one this record already meets — a retrospective record says that it is one”.

   **Source:** Amended RFC 0000, L58–59, additionally requires the record to describe existing work and state **implementation, release and review standing of each part**. The adoption paragraph presents retrospective labeling as the condition. Evidence explicitly distinguishes implementation, release and demonstration status, but does not state review standing for every part—for example, the receipt format and verifier join have no review-standing statement.

   **Smallest edit:** Refer to the complete conditions in RFC 0000, and state the missing review standing briefly, with supporting references or an explicit statement that it was not established. This requires disclosure, not additional review machinery.

6. **R5-F6 — MINOR: directory descriptions still assume prospective proposals that produced subsequent text.**

   **At issue — `rfcs/README.md`, L8–11:** an accepted RFC’s “text it produced lives where the proposal declared it would land”.

   Related descriptions remain “Open change proposals” in `README.md` L155, “Open Requests for Comments — design proposals” in `web/build.py` L412, and “Open design proposals and the change process” at L1980.

   **Source:** The newly added index paragraph expressly says RFC 0014 records governing texts that preceded it. Acceptance produced neither those texts nor their adoption.

   **Smallest edit:** Replace “the text it produced” with “the governing text”, qualifying the prospective case if needed. Describe the directory as holding “open proposals, accepted design records, and the process”.

The disposition itself is permitted. RFC 0000 distinguishes acceptance at the named maturity from stabilization, and applies the two-independent-implementations bar to stable normative features. RFC 0006’s adoption record establishes the same maturity distinction. RFC 0014 expressly claims exploratory endorsement only.

I found no prohibition on amending RFC 0000 in the benefiting PR. The process question is explicitly identified and the simultaneous amendment plainly disclosed. It remains subject to the ordinary public-review, cross-vendor-review and maintainer-disposition requirements. The new paragraph does not confer authority over another repository or waive the stability bar.

- The agreement test exists, covers Postgres and two records, and has both fixture and fresh-fetch tests. The quoted scope and omitted value types match its design note.

Its CHANGELOG identifies ADR-0034. Gateway [tag references](https://api.github.com/repos/Judgment-Pack/judgment-pack-gateway/git/matching-refs/tags/) still contain only v0.1.0 and v0.2.0.
- All four listed developments appear in the promised locations. The scope-note and Unresolved 8 changes are separately disclosed as the process ruling. Apart from F1, I found no improperly struck substantive claim.
- I found no further source-backed contradiction in Alternatives, Compatibility, Conformance, the placement table or the remaining unresolved questions. All twenty version-3 store vectors remain present.
- RFC 0015 already acknowledges `verify-ts` without claiming independence. RFC 0003’s clean-room discussion concerns version 2, and its two-back-end bar remains unmet. Neither becomes false through this acceptance. No acceptance-related correction surfaced in `docs/architecture/vision.md` or `FAQ.md`.

**Required fixes: R5-F1 through R5-F6.** The substantive retrospective ruling can stand.
