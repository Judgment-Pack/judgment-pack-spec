## Findings

### 1. HIGH: §9.3's `dependencies` "absent otherwise" contradicts the reference Runner for every acquired source that declares a source parameter

**Where:** `spec/dialect.md:1127` and `:1143`, equal in `rfcs/0018-dialect.md:1740` and `:1756`; the
readers at `tools/dialect_verify.py:2702` (`if outcome.skipped:`) and
`tools/dialect-verify-ts/src/prepare.ts:659` (`if (o.skipped) {`); the PR body ("acquired targets
have none").

**What happens.** The new row says `dependencies` is "all source parameters for a skipped source,
as below; absent otherwise". The new paragraph ends: "No acquired source's entry carries
`dependencies`, including one whose claim is `unknown`." The Runner at `ed1bc2a` does not write
that form:

- it builds `deps` from every declared source parameter of every source, before the availability
  test (`internal/runner/mapping_v2.go:350–359`);
- it passes `deps` to `merge` unconditionally (`:534`, into `TargetLineage` at `:307` and `:317`);
- the member is `json:"dependencies,omitempty"` (`mapping_v2_types.go:155`), so it is dropped only
  when a source declares no source parameter;
- `docs/MAPPING-V2.md:610–611` documents it: "Each lineage entry names … dependency pointers".

The staged vector cannot tell the two rules apart. Its two acquired sources declare no parameters,
and its one source with parameters is skipped. Runner PR 105's unit test checks only sources
without parameters too.

**Confirmed by running:**

- **The Runner writes it.** I ran a probe in a scratch copy of the Runner
  (`.review-scratch/runner_probe_test.go.txt`, log `.review-scratch/runner-probe.log`). It uses the
  vector's own `skippedSourceInput`, with `sponsor`'s record naming `S-1` and `endorsement`
  acquired. `endorsement`'s two entries carry `dependencies` (`approver` from `sponsor`, then
  `requestType` from `intake`). They do so when its claim is `resolved` and again when it is
  `unknown` (`not-endorsed`).
- **Neither reader accepts it.** Both amended readers answer `preparation-differs` on each of those
  Runner preparations (`.review-scratch/acquired-dependent/{resolved,unknown}`). With only the
  `dependencies` members removed, both give a reading.
- **Nothing in the PR tells the two rules apart.** Mutant m6 makes both readers write
  `dependencies` for every source that declares a source parameter, which is the Runner's rule. It
  passes all 82 `test_dialect*` tests, the cross-reader test among them, and `npm test` 101/101.

So neither reader can verify a genuine Runner export in which a dependent source is acquired, which
is the ordinary use of a source parameter. And round 12 states as a rule the one form the Runner
does not write, under a decision whose premise is "the text takes the reference Runner's form".
The RFC's own Compatibility bullet calls such a difference "a defect in the text".

**Fix:** take the Runner's rule.

- **The row:** "the source's declared source parameters, as below, for every source that declares
  one, acquired or skipped; absent for the case, a local file and a source that declares none".
- **The paragraph:** replace its last sentence. An acquired source whose parameters all have values
  carries them too.
- **The readers:** both drop the `skipped` condition. In Python,
  `if outcome.source is not None and outcome.source.parameters:`; the same in TypeScript.
- **The tests:** add a hand-written case to both readers' units and to the cross-reader cases. Use
  the vector's inputs with `sponsor` resolving and `endorsement` acquired, signed with the tests'
  own key as `altered_vector` does.
- **The Runner:** ask it for a vector of an acquired dependent source.

If the maintainer wants "skipped only" instead, the Runner must change for every preparation with an
acquired dependent source. That is option B for this member, and it needs its own decision before
the text states it.
